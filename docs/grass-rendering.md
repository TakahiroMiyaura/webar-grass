# 草アセットと描画（MYAA-17）

草の生成パイプラインと、モバイル向けに最適化した描画モジュール `GrassField` の設計メモ。

## ファイル

```
src/xr/grass.ts         GrassField 本体
src/xr/tuft-geometry.ts カード形状の生成（three 以外に依存しない。理由は後述）
src/xr/perf.ts          フレーム計測 / 適応解像度
bench.html + src/bench.ts  実機で fps を測るベンチページ（Vite のもう 1 つの entry）
src/assets/
  grass.glb           草 1 株（3 枚クロスカード）+ アトラス埋め込み
  grass-atlas.png     2x2 の草アトラス（4 バリエーション）
  grass-atlas.ktx2    KTX2/ETC1S 版（既定では未使用。後述）
  shadow.png          接地影
  tuft-card.json      GLTFLoader なしで同じ形状を組むためのカード定義
tools/                アセット生成・圧縮比較・headless 計測
```

アセットは生成済みでコミットしてあるので、サイトを動かすだけなら `tools/` は要らない。
再生成するときだけ `npm run assets`
（検証 `npm run assets:verify` / 圧縮比較 `npm run assets:compress` / 計測 `npm run bench`）。

`src/assets/` に置いて `import` しているのは、Vite にハッシュ付きで `dist/assets/` へ出させるため。
`public/` に置くとサブパス配信時の URL 解決を自分で面倒みることになる。
`tuft-card.json` は `import` でそのまま JS に載るので、実行時の fetch は発生しない。

## 使い方

```ts
import {GrassField} from './grass'

const grass = await GrassField.createProcedural({scene, renderer, capacity: 900})

// タップ時（MYAA-16 の hitTest 結果を渡す。法線が無ければ null で可）
grass.plant(hit.position, null)

// 毎フレーム
grass.update(elapsedSeconds, camera)
```

`src/xr/scene.ts` の `onTap` で立方体を置いている箇所を差し替えれば繋がる。
**このタスクでは `scene.ts` に手を入れていない**（MYAA-16 が同じ箇所を持っているため）。

主なオプション（既定値は `grass.ts` の `DEFAULTS`）：
`capacity` / `perTap` / `tapRadius` / `height` / `growSec` / `wind` / `cullNear` / `cullFar` /
`shadows` / `shadowScale`。

GLB から読みたい場合は `GrassField.create({scene, renderer})`。形状は両経路で同一で、
`npm run assets:verify` が GLB と手続き生成を突き合わせる（実測の最大差 3.3e-6 ＝ float32 の丸めのみ）。

## 設計と、その理由

### 1 ドローコール

草は 1 つの `InstancedMesh`。見た目のバリエーションはアトラスの 2x2 セルを
**頂点シェーダで instance ごとに選ぶ**ことで出しているので、4 種類あってもドローコールも
テクスチャバインドも増えない。接地影がもう 1 本。

### CPU では何もアニメーションさせない

生長・風・消滅の縮みはすべて `uTime - plantTime` の関数として頂点シェーダで解いている。
`instanceMatrix` は植えた瞬間に 1 回書いたきり、以後触らない。

素直に毎フレーム行列を作り直して `needsUpdate` を立てると、900 株で
**毎フレーム 57KB の再アップロード**になり、モバイルのバス帯域に直接効く。

書き込みも `addUpdateRange()` で触ったスロットだけに絞ってある
（three は `updateRanges` が空だとバッファ全体を上げ直し、隣接レンジは自動でマージする）。

### 予算は三角形ではなくフィルレート

アルファテストの草はモバイルのタイルベース GPU で early-Z が効かないため、
**discard される画素にもフラグメントシェーダのコストがかかる**。
アトラスの不透明率は 15.8% しかないので、板ポリ 1 枚だと塗る量のほとんどが捨てられる。

そこでカードをアルファの形に沿って縦に切り詰めてある（`tools/fit-card.mjs`）：

| カード形状 | 三角形 / カード | ラスタライズ面積 |
|---|---|---|
| 板ポリ 1 枚 | 2 | 100% |
| **切り詰めカード（8 列・採用）** | **12** | **53.2%** |

頂点は安く、フィルは高い。三角形を 6 倍払って塗る量を **46.8% 減らす**のは明確に得な取引。
1 株 = 3 枚クロス = 36 三角形。900 株でも 32,400 三角形で、これは問題にならない量。
列数ごとの面積は `tools/analyze-card.mjs` で出せる（12 列以降は頭打ち）。

同じ理由で：

- マテリアルは **`MeshBasicMaterial`**（ライトなし）。縦の陰影はアトラスに焼いてある。
  AR の光源推定はそもそも当てにならないので、SLAM が食っている GPU で
  ピクセルごとのライティングを回す価値がない
- 接地影は四角ではなく **10 角形**。丸いブロブに対して四角の角は約 27% の無駄
- 遠方の草は頂点シェーダでスケール 0 に潰す。縮退三角形はフラグメント処理の前に
  捨てられるのでフィルがまるごと浮く（既定 3.0m から消え始め 4.0m で消滅）

### アトラスの作り

- **セル間に 8px のガター**。ミップの補間が隣のセルの草を拾わないようにするため
  （ガター内の不透明テクセル数 = 0 を検証済み）
- 透明部分の RGB は**中間の緑で塗り潰し**てある。SVG のまま黒にしておくと、
  ミップが下がった瞬間に葉の縁に黒いフリンジが出る（アルファテスト植生の定番の破綻）
- `alphaTest` は 0.5 ではなく **0.35**。ミップはアルファテストのシルエットを痩せさせるので、
  少し下げておかないと遠くで葉先から溶ける
- 葉の根元幅は 11px 以上を維持（数段のミップに耐えるため）

### 接地影

`MultiplyBlending` で**カメラ映像を暗くする**方式。灰色の円を上から描く方式と違い、
白い机でも黒い机でも破綻しない。草の根元より 4mm 下に沈めてあるので深度テストで草自身に隠れる。
重なると乗算が累積するため、テクスチャの中心は暗くしすぎないようにしてある。

three r183 の `MultiplyBlending` は `premultipliedAlpha: true` を要求し、
`dst*src + dst*(1-srcAlpha)` になる。影テクスチャは不透明なので素の乗算に落ちる。

## 圧縮：Draco と KTX2 は、この規模では逆効果

課題の指示は Draco + KTX2 だったので、全組み合わせを作って**実測**した（`tools/compress.mjs`）。
比較の単位は「初回ロードでネットワークに乗る合計バイト数（gzip 後）」で、`.glb` 単体ではない。
デコーダも数える必要がある。GitHub Pages は **gzip のみ・brotli なし**なので gzip で揃えてある。

| 経路 | .glb gz | デコーダ gz | 合計 gz |
|---|---|---|---|
| **plain（採用）** | **24.7 KB** | **0** | **24.7 KB** |
| Draco | 24.6 KB | 73.3 KB | 97.9 KB |
| KTX2 | 35.1 KB | 256.5 KB | 291.6 KB |
| Draco + KTX2 | 35.0 KB | 329.8 KB | 364.8 KB |

- **Draco は明確な損**。ジオメトリは 72 頂点しかないので gzip 後で 0.1KB しか縮まないのに、
  デコーダに 73KB 払うことになる
- **KTX2 も今回は損**。パレット量子化した PNG（23.8KB）より KTX2/ETC1S のほうが
  ファイル自体が大きく（39.2KB）、さらに basis transcoder が 256KB 乗る

テクスチャは PNG のパレット量子化のほうが効いた：**61.5KB → 23.8KB**。
量子化前後を実行時と同じ `alphaCutoff` で二値化して比較したところ、反転するテクセルは
**0.045%** で、アルファテスト後のシルエットは実質変わらない。

### KTX2 を入れるべきタイミング

KTX2 が効くのは VRAM で、そこは 4 倍効く：

| | GPU メモリ（512x512 + ミップ） |
|---|---|
| PNG → RGBA8 | 1365 KB |
| KTX2 → ASTC 4x4 | 341 KB |

テクスチャ 1 枚に 256KB の transcoder を払うのは割に合わないが、
**テクスチャ総量が 4MB を超えたあたりで逆転する**。`grass-atlas.ktx2` は生成済みなので、
アセットが増えたら切り替えられる。`tools/compress.mjs` を再実行すれば判断し直せる。

### GLTFLoader も同じ話

**ここは Vite 移行（MYAA-13）で数字が変わったので訂正しておく。**
素の `<script type=module>` で vendor していたときは `BufferGeometryUtils` と `SkeletonUtils` を
引き連れて **35.3 KB gz** だったが、Vite だと tree-shake され three 本体を共有するので
**GLTFLoader チャンクは 13.2 KB gz**（`dist/assets/GLTFLoader-*.js`）まで下がる。

それでも読み込む対象のジオメトリは 3.6 KB で、しかも**別リクエスト 1 本**増える。
`GrassField.createProcedural()` を既定に据える判断は変わらないが、**差は当初より小さい**。

`GrassField.create()` を残してあるのは**アセットの差し替え口として**。デザイナーが
`grass.glb` を差し替えられることに価値があるなら、13.2 KB は十分払える額。
動的 `import()` なので、`create()` を呼ばない限りチャンクは落ちてこない。

### 実際の配信サイズ

`npm run build` 実測（`dist/`）：

```
assets/grass-atlas-*.png   24.4 KB      （gzip 後もほぼ同じ。PNG は既に deflate 済み）
assets/grass-*.glb         28.3 KB      （GLB 経路を選んだ場合のみ）
assets/GLTFLoader-*.js     13.2 KB gz   （同上。動的 import なので既定では落ちてこない）
shadow.png                 —            （702 B なので Vite が data URI にインライン化）
tuft-card.json             —            （JS バンドルに同梱。リクエストは発生しない）
```

three 本体だけで 182.7 KB gz、エンジン本体が gzip 後で約 2.2 MB あるので、
**草アセットは初回ロード全体の 1% 程度**。ここをこれ以上削っても体感は変わらない。

## 「100 株で 30fps」の確認について

**この完了条件はまだ満たしたと言えない。実機が無いため。**

CI ランタイムには GPU が無く、Chromium は SwiftShader（ソフトウェアラスタライザ）に落ちる。
そこで出る絶対 fps はミドルレンジのスマホと何の関係も無いので、報告していない。

### headless で分かること（device 非依存）

`tools/bench.mjs` の出力。**絶対値ではなく比だけ**に意味がある。

- シェーダが正しくコンパイルされる
- **ドローコール 3 本**（カメラ映像相当の全画面転送 + 草 + 接地影）。草は何株でも 1 本
- 草 100 株で 4,602 三角形、900 株で 32,400 三角形

**フレーム時間は株数ではなく画素数に比例する。** ここが設計の前提であり、
チューニングの優先順位を決める根拠でもある。

| 画素数（DPR） | 画素比 | フレーム時間比 |
|---|---|---|
| DPR 1.0 | 1.00x | 1.00x |
| DPR 1.5 | 2.25x | 3.03x |
| DPR 2.0 | 4.00x | 4.41x |

| 株数（DPR 1.0 固定） | 株数比 | フレーム時間比 |
|---|---|---|
| 100 株 | 1.00x | 1.00x |
| 300 株 | 3.00x | 1.51x |
| 600 株 | 6.00x | **1.73x** |

**株数を 6 倍にしても 1.73 倍にしかならないのに、DPR を 2 倍にすると 4.4 倍になる。**
草を減らすより先に解像度を下げること。1 株ずつが重いのではなく、重なった草が同じ画素を
何度も塗るのが重い（`InstancedMesh` なのでドローコールは増えない）。

**接地影は無料ではない。** 300 株・DPR 1.0・カメラ映像なしで測ると、

| | フレーム時間 |
|---|---|
| 接地影 OFF | 150.2 ms |
| 接地影 ON | 221.2 ms（**1.47x**） |

影は乗算合成の円盤なので、草のカードと違って**自前のフィルを一切削れない**（discard が無い）。
`shadowScale` を 1.7 から 1.3 に絞ってあるのはこのため（面積は 2 乗で効く）。
それでもこの比なので、実機で足りなければ `shadows: false` は現実的な選択肢。
なお SwiftShader の絶対値なので、実 GPU のブレンド性能では比が変わる可能性がある。

### 実機での測り方

`bench.html` をスマホで開き（公開 URL なら `<公開URL>/bench.html`）、**「自動計測」**を押す。
草 100/300/600/900 株 × DPR 1.0/1.5/2.0 の 12 通りを自動で回して、
それぞれの平均 fps と **p95 fps** を出す。

p95 を見ているのは、20 フレームに 1 回のカクつきは平均には出ないが人間にははっきり分かるため。
**p95 が 30fps を超えていれば合格**とする。

ベンチは SLAM を回していないので**上限値**になる。カメラ映像相当の全画面転送は入れてあるが、
SLAM の CPU/GPU 消費は再現できない。MYAA-16 で草が本編に繋がったあと、
本編で出る数字との差がそのまま SLAM の取り分。

### 数字が足りなかったときに効く順

1. **`src/xr/canvas.ts` の `MAX_PIXEL_RATIO`（現在 2）を 1.5 か 1.25 に下げる**
   （**フィル律速なので圧倒的に一番効く**。ただしこの定数は草だけでなくカメラ映像の
   転送にも効くアプリ全体の設定なので、このタスクでは変更していない）
2. `src/xr/perf.ts` の `AdaptiveCanvasScaler` に切り替えて自動で落とす
3. `shadows: false`（測定値で 1.47x。影は自前のフィルを削れないので効果が大きい）
4. `cullFar` を 4.0m から 2.5m に縮める
5. `capacity` と `perTap` を下げる（**株数はいちばん効かない。6 倍で 1.73 倍**）
